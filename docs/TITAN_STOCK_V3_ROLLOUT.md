# TITAN — stock v3 staging and rollout evidence gate

**Status:** Source-only instructions, not authorization to write production stock. The authenticated operator stock page is **read-only by default**; `LINEN_STOCK_WRITES_ENABLED=enabled` is a separate explicit server-side approval, never a browser setting. **That flag alone never permits stock movements:** the API also requires the authenticated service-role `public.fabric_stock_write_ready_v1()` RPC to return the literal boolean `true`, checking the database at each privileged write and before advertising writable status. Missing RPC, invalid grants, mismatched migration, timeout, or non-boolean response means read-only GET and a definitive 423 on POST. A passing CI test does not constitute a production rollout.

## Confirmed connected-state blocker (read-only inspection, 2026-11-02)

The connected `llinen-earth-designer` Supabase project runs PostgreSQL 17.6. Its `fabric_stock_snapshot_v2(text[])` and `fabric_stock_reserve_v2(...)` functions exist, but **`fabric_stock_record_v3(...)` does not**. No Supabase development branch was available when checked. Creating a development branch may incur charges and requires owner approval; these instructions create no branch and change no live SQL. The Supabase security advisory reports RLS enabled/no policies for multiple `private` tables (informational; deny-by-default is deliberate and must not be “fixed” with broad policies).

## Migration inventory and controlled sequence

Use a **separate isolated, access-controlled Supabase staging database** (never a live connection disguised as staging). Record the staging project/branch ID, PostgreSQL version, authorized owner, backup/snapshot restore point and time before touching schema.

1. With **stock writes disabled**, verify the staging project contains the existing v2 stock ledger, snapshot and reservation functions, and no pre-existing unreviewed divergent SQL versions. Snapshot real staging data/roles/configuration for restore; check off-site or documented backup recoverability.
2. Run the non-mutating, catalog-only check: `psql -X -v ON_ERROR_STOP=1 -At -f scripts/stock-v3-readonly-preflight.sql | jq .`. Before deploying stock v3, its expected status is **BLOCKED** (missing v3). The query examines function existence, SECURITY DEFINER, fixed search_path, service_role grants, anon/authenticated denials **and static source-shape checks for both v3 receipt and v2 reservation request-key payload binding**. In particular, a legacy reservation function with the same public signature and privileges must report **BLOCKED**, even if v3 is installed. CI deliberately installs the legacy body while v3 is present, verifies BLOCKED, then reapplies the reviewed binding migration and requires READY. The M71 catalog guard additionally rejects fixed `search_path` configurations containing `pg_temp` or unknown schema entries; only the reviewed `public` and `public,private` paths are accepted. M74 further rejects internal whitespace in individually quoted names (for example `"pub lic"` and `public,"priv ate"`) rather than deleting whitespace before validation; the shared strict rule still permits ordinary spacing around the comma. Disposable PostgreSQL CI covers both forms and confirms rollback. The M73 parser preserves quoted identifier boundaries, so one schema named `"public,private"` cannot masquerade as two allowed schemas; disposable CI checks both stock readiness and standalone preflight and restores the original SQL definition. The independent read-only staging preflight applies the identical allowlist, with disposable CI asserting **BLOCKED** under `public,pg_temp` and **READY** again after rollback; the web readiness RPC and staging report must not disagree. Disposable CI tests a temporary unsafe path and requires both rejection and clean rollback. These code-shape checks only catch known missing safeguards; they do not prove semantics against a maliciously modified function. Actual replay and mismatch tests remain mandatory. It does **not** read or mutate customer/fabric ledger rows.
3. Apply only the review-approved source migrations to **staging**, using the same ledger-compatible ordering as CI: `supabase/migrations/20261102_stock_reservation_key_payload_binding.sql` (after v2 stock/20261031 reservation migrations), followed by `supabase/migrations/20261102_stock_record_idempotency.sql` and `supabase/migrations/20261102_stock_write_readiness_v1.sql`. The last service-only function reads catalogs but does not read or mutate fabric ledger records. Use a verified staging-only connection; do not substitute production project credentials. Refresh PostgREST schema cache.
4. Re-run the catalog-only SQL. Require **READY**, five installed stock movement/snapshot functions, fixed search_path, service-role execute, anon/authenticated denied; inspect all per-function results. The M75 schema-grant gate additionally requires `schema_create_isolated=true`: neither `anon` nor `authenticated` may have inherited CREATE privilege in `public` or `private`, because the trusted SECURITY DEFINER search path must not contain schemas writable by ordinary API callers. Disposable PostgreSQL CI temporarily grants these privileges in isolated transactions, requires both the backend attestation and independent staging preflight to block writes, and proves READY is restored after rollback. Separately, verify service-role RPC `fabric_stock_write_ready_v1()` returns the literal SQL boolean `true` and anonymous/authenticated callers cannot invoke it. **READY is only schema/permissions readiness**, not supplier truth or approval to enable writes.
5. On synthetic **staging-only** roll/locked design records, verify 0.001m quantities, exact request-key replay and mismatched-payload rejection; reserve/consume/release; concurrent stock adjustment, lost acknowledgment and retry; an authenticated operator, forged/unauthorized caller and CSRF rejection. Keep identifiers uniquely prefixed; capture SQL balances, event counts and redacted logs. Test both `LINEN_STOCK_WRITES_ENABLED` unset (**read-only**) and explicitly `enabled` on **staging only**.
6. Exercise full **restore**, not merely `DROP FUNCTION`: restore staging data and SQL functions to the captured baseline, including the original `fabric_stock_reserve_v2` definition, permissions, PostgREST cache, reservation linkage, and retry behavior. The M69 readiness function must return false when the original version is restored or v3 is absent, and be dropped when restoring the pre-M69 baseline. The **M67 disposable PostgreSQL 17.6 rehearsal** captures the original pre-upgrade reservation function with `pg_get_functiondef`, checks its saved SHA-256, restores that exact SQL after removing v3, verifies byte-identical function text and service-only privileges, refreshes PostgREST, and confirms the read-only preflight returns **BLOCKED** again. This is stronger than the earlier v3-drop-only rehearsal but **still is not** a full Supabase project backup restoration: actual data, auth, extensions, storage, configuration and provider restore mechanisms must be separately exercised in approved isolated staging.
7. Record exact integrated repository commit, CI/QA run IDs, staging database identity (non-secret), migration checksums, before/after catalog preflight output, synthetic-ledger evidence, restoration evidence and independent human signoff. Mark unknown evidence **not verified**, not passed.

## Physical and business release gates

The staging database cannot certify real available stock. Require supplier/roll identities, measured composition/GSM, meterage, pattern repeat and provenance, verified cutting-card evidence, tailor measurements/usage, five full-journey testers, ten actual production deliveries, mobile/desktop accessibility and security evidence, final model/photo/UV acceptance, and launch-owner signoff. Physical stock opening figures must come from real measurements, never synthetic fixtures or a simulated snapshot.

## Production change control

No rollout until all criteria above pass **and** the owner explicitly authorizes the production migration and subsequent flag change. Create a change window, approved backup and tested restore, staged permissions review and an on-call reconciliation plan. Apply reviewed migration first with **writes still disabled**, confirm catalog-only preflight and read-only GET, then enable the server flag in a separately approved release. An already-open tab with stale permissions receives **HTTP 423 Locked** on its next mutation (a definitive pre-RPC refusal), immediately switches all stock buttons to read-only and clears its temporary pending marker. Distinguish this from 502/503, timeout or malformed acknowledgments, which may have committed and require physical reconciliation. If there is any uncertainty, disable the flag first to halt new writes, preserve ledger and physical evidence, reconcile ambiguous actions by their original request keys and use the tested restore plan only under approved change control. Do not use a blanket ledger delete or casual destructive rollback on production.
